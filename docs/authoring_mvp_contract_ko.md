# 초보자용 규정 작성 MVP 계약

기준일: 2026-08-30

## 1. 목적

이 기능은 원문 파일이 없는 초보자가 질문형 안내를 따라 규정 초안을 만들고,
사람이 확인한 초안 패키지를 내보낼 수 있게 한다. 작성 기능은 기존의 전처리,
공식 검수·승인, 승인 벡터 색인, MCP 공개 절차와 분리한다.

작성 화면과 출력물의 `내용 동결`은 편집 기준본을 고정했다는 뜻일 뿐 법적 검토,
기관 결재 또는 기존 시스템의 `approved` 상태를 뜻하지 않는다.

## 2. 안전 경계

- 작성 프로젝트는 `data/authoring` 아래의 별도 저장소에 둔다. 테넌트 격리가
  켜지면 기존 `settings_for_tenant`가 만든 테넌트별 `data_dir` 아래에 둔다.
- 작성 기능은 `Document`, `Chunk`, 승인 저널, 승인 해시, 벡터 저장소 및 MCP
  번들에 쓰지 않는다.
- P0은 JSON/Markdown 초안 패키지 내보내기까지만 제공한다. 기존 전처리
  파이프라인으로 가져오는 기능은 별도 보안 검토가 끝난 뒤 P1에서 추가한다.
- 모든 API는 명시적 기능 플래그를 통과해야 하며, 읽기와 쓰기 모두 테넌트
  소유권과 canonical 기관 프로필 범위를 다시 확인한다. 프로젝트 목록을 포함한
  모든 프로젝트 작업에는 현재 기관 프로필 ID가 필요하다.
- 작성 API의 읽기·쓰기는 `admin` 또는 `operator`에게만 허용한다. 보호 환경에서
  동결하려면 작성·수정한 사람과 다른 인증된 행위자가 확인해야 한다.
- 로컬 비인증 모드의 자기 동결도 기본 거절한다. 요청자가 연습용 자체 확인을
  명시적으로 선택하고 사유를 적은 경우에만 허용하며, 프로젝트와 내보내기 결과를
  연습용 상태와 `공식 승인 아님`으로 영구 표시한다. JSON은
  `training_only=true`, Markdown은 `연습용 표시: 예`를 사용한다.
- 클라이언트가 마지막으로 본 개정 번호를 모든 변경 요청에 보내게 하고,
  불일치하면 `409 Conflict`로 막는다.

## 3. 용어와 상태

공식 승인과 혼동되는 `approved`, `approval_id`, `approved_content_hash`는 작성
스키마에서 사용하지 않는다.

작성 상태는 다음과 같다.

1. `planning`: 목적과 기본정보를 정리하는 단계
2. `drafting`: 조문을 작성하는 단계
3. `review_requested`: 작성자가 내용 확인을 요청한 단계
4. `changes_requested`: 수정 요청이 기록되어 다시 작성해야 하는 단계
5. `content_frozen`: 특정 개정본의 내용이 동결된 단계
6. `exported`: 동결본을 초안 패키지로 내보낸 단계
7. `abandoned`: 작성 작업을 중단한 단계

허용 전이는 다음과 같다.

- `planning -> drafting`
- `planning -> abandoned`
- `drafting -> review_requested | abandoned`
- `changes_requested -> drafting | abandoned`
- `review_requested -> changes_requested | content_frozen`
- `content_frozen -> drafting | exported`
- `exported -> drafting`

동결 또는 내보낸 프로젝트를 다시 편집하면 이전 결과를 덮어쓰지 않고 새 개정
번호로 `drafting`에 돌아간다.

## 4. P0 사용자 흐름

1. 기관 프로필을 선택한다.
2. `새 규정` 또는 `기존 규정 개정안`을 고른다. P0 개정안은 기존 승인
   카탈로그를 자동 선택하지 않고 대상 규정명·버전 또는 시행일을 직접 입력한다.
3. 규정명, 목적, 적용 범위, 근거, 담당부서와 시행 예정일을 입력한다.
4. 범용 템플릿에서 생성한 조문 골격을 쉬운말 안내에 따라 채운다.
   P0의 조문 ID·유형·부모·순서·번호·제목·필수 여부와 안내 문구는 서버가
   소유하는 템플릿 계약이며, 사용자는 조문 본문과 근거 연결만 편집한다.
5. 결정론적 검사를 실행해 필수정보, 빈 조문, 번호 중복, 내부 참조 오류를
   확인한다.
6. 프로젝트를 내용 확인 대기 상태로 바꾼다.
7. 로컬 1인 연습 화면에서는 검토 시트를 다시 읽고, 명시적 연습 선택과 사유가
   있을 때만 특정 개정본을 자체 동결한다. 연습용 표시는 영구 보존된다.
8. `공식 승인 아님` 표시가 포함된 JSON 또는 Markdown 초안 패키지를 내보낸다.
9. 세션이 바뀌어도 저장된 export 이벤트의 형식·파일 SHA-256과 동결 manifest를
   검증해 같은 패키지를 새 개정 없이 다시 내려받을 수 있다.

보호된 2인 실무 흐름에서는 P0 밖의 별도 채널로 확인자에게 알리고, 작성 행위와
분리된 확인자 계정이 보호 모드 API에서 동결한다. 자동 알림과 결재선은 제공하지
않으며 로컬 자체 동결은 이 경로를 대신하지 않는다.

각 단계는 초보자에게 다음 행동 또는 필요한 결정을 우선 안내하며, 오류는 위치와 수정
방법을 함께 보여 준다.

## 5. 최소 데이터 계약

작성 프로젝트에는 다음을 저장한다.

- 추측하기 어려운 UUID 프로젝트 ID
- 테넌트 ID, 기관 프로필 ID, 작성 모드와 템플릿 버전
- 규정명, 목적, 적용 범위, 법적·내부 근거, 담당부서, 시행 예정일, 개정 사유
- 순서가 있는 장·절·조·항·호 초안 노드
- 작성 상태, 단조 증가하는 개정 번호, 의미 내용 해시
- 생성·수정·검토 요청·수정 요청·동결·내보내기 행위자와 UTC 시각
- tenant 프로젝트 snapshot의 최신 수정 요청 문구와, 자유문 대신 제공 여부·해시만
  남기는 내용 없는 불변 전이 이벤트
- 검사 결과와 `training_only` 표시

API 키, 시스템이 만든 로컬 절대 경로와 기관별 비공개 운영 식별자는 오류 응답,
감사 로그와 공개 소스에 포함하지 않는다. 사용자가 초안 본문이나 근거 항목에
의도적으로 입력한 내용은 권한이 확인된 작성 프로젝트 응답과 출력물에만 나타난다.

## 6. 검증 기준

- 기능 플래그가 꺼지면 작성 API는 실패 폐쇄한다.
- 다른 테넌트는 프로젝트 존재 여부를 유추할 수 없게 동일한 `404`를 받는다.
- 오래된 개정 번호로 저장하거나 동결하면 `409`가 발생한다.
- 허용되지 않은 상태 전이는 프로젝트 이벤트를 추가하지 않고 거절하며, API
  요청이면 내용 없는 실패 결과를 API 감사 로그에 남긴다.
- 필수 오류나 완료하지 않은 작성자 확인 목록이 있으면 검토 요청과 동결을 차단한다.
- API 요청도 P0 조문 템플릿의 추가·삭제·재정렬·번호 변경·필수 여부 변경을
  거절하고, 거절된 요청은 개정 번호나 이벤트를 만들지 않는다.
- 보호 환경의 자기 동결은 거절된다.
- 로컬 자기 동결 결과에는 연습용 경고가 영구적으로 남는다.
- 작성 전 과정을 수행해도 승인 저널과 승인 벡터 파일은 새로 생기거나 바뀌지
  않는다.
- 내보내기 실패 시 프로젝트와 기존 공식 저장소는 일관된 상태를 유지한다.
- snapshot과 event는 manifest 공개 전에 저장된 바이트와 event hash chain을 다시
  검증하며, 이 단계가 실패하면 새 상태·개정·이벤트를 공개하지 않는다.
- 최초 snapshot 전에는 본문 없는 tenant·기관·project staging intent를 먼저
  기록한다. 강제 종료 뒤 manifest가 없는 generation은 시작 시 복구하고, 기관 삭제
  계획과 정리도 남은 intent를 발견해야 한다.
- 저장과 조회 시 선언된 의미 내용 해시를 실제 canonical 작성 내용으로 다시
  계산하고, 내보내기는 최신 화면이 아니라 정확한 동결 개정 snapshot만 사용한다.
- 미저장 화면 입력의 기준 개정은 자동 승격하지 않는다. 다른 화면에서 개정이
  바뀌면 저장·검사·상태 변경을 막고 명시적인 최신 개정 불러오기를 요구한다.
- 초안·입력 구역별 세션 버퍼로 프로젝트 왕복과 부분 저장 뒤에도 미저장 값을
  복원한다. 같은 초안에서 한 구역의 로컬 저장이 성공한 경우에만 다른 미저장
  구역의 기준 개정을 그 결과로 갱신하며, 기관 전환은 현재 기관의 모든 초안 버퍼를
  검사한다. 브라우저 세션 종료 전에는 각 구역을 서버에 저장해야 한다.
- 모든 브라우저 작성 상태와 내보내기 캐시는 tenant·기관 프로필·프로젝트 범위를
  함께 사용한다. 캐시 파일은 현재 동결 개정과 내용·파일 해시가 모두 맞는
  `exported` 프로젝트에서만 다운로드할 수 있고, 재개 시 즉시 제거한다.
- 로그와 오류 응답에는 초안 본문이나 로컬 경로를 넣지 않는다.
- 작성 API의 schema validation 422와 본문 크기 413도 입력값을 반사하지 않고
  내용 없는 감사 레코드를 남긴다. multipart 예외는 실제 `/api/documents` 업로드에만
  적용하고 authoring 경로에는 Content-Type과 관계없이 제한한다.
- 기관 프로필과 데이터를 함께 삭제하면 같은 tenant·기관 프로필의 작성 초안과
  내보내기도 삭제하며, 부분 실패는 다음 시도에서 계속할 수 있어야 한다.
- 내보내기 artifact와 `EXPORTED` 전이는 기관 삭제와 같은 저장소 잠금에서
  커밋하여, 삭제 완료 뒤 진행 중이던 요청이 고아 파일을 다시 만들 수 없어야 한다.

## 7. 후속 단계

P1은 결정론적 문장·구조 검사 강화, 로컬 또는 명시적으로 허용된 AI 제안,
기존 승인 규정에서 개정안 시작, DOCX 내보내기, 기존 전처리로의 1회성 가져오기를
다룬다. 가져오기는 새 `Document`를 `draft` 또는 `pending_approval`로만 만들고,
청크를 자동 승인하거나 색인하지 않아야 한다.
