# 규정 작성 기능 보안 모델

기준일: 2026-08-30

## 보호 대상과 신뢰 경계

규정 작성 기능은 아직 법적·기관 결재를 거치지 않은 초안을 다룬다. 보호 대상은
초안 본문, 작성자 식별자, 기관·테넌트 귀속, 개정 이력, 동결본의 내용 해시와
내보내기 결과다.

작성 저장소와 기존 공식 처리 저장소 사이를 가장 중요한 신뢰 경계로 본다.
P0에서는 이 경계를 통과하는 자동 import를 제공하지 않는다. 작성 서비스는
`Document`, `Chunk`, 승인 저널, 승인 벡터 및 MCP 번들을 읽거나 쓰지 않는다.

## 위협과 필수 통제

### 테넌트 간 초안 노출

- 모든 프로젝트와 이벤트에 canonical tenant ID를 저장한다.
- API는 요청 테넌트에 맞춘 설정과 저장소만 사용한다.
- 목록, 조회, 변경, 동결, 내보내기에서 저장된 tenant ID를 다시 확인한다.
- 다른 테넌트의 ID를 제시해도 존재 여부를 알 수 없도록 `404`로 응답한다.

### 같은 테넌트 안의 기관 프로필 혼선

- 기관 프로필 ID는 기존 프로필 레지스트리 규칙으로 canonical 소문자화한다.
- 목록을 포함한 모든 프로젝트 작업은 현재 기관 프로필 ID를 명시해야 한다.
- 저장된 프로젝트와 요청 프로필이 다르면 같은 테넌트여도 누락된 프로젝트와 같은
  `404` 경로로 처리한다. 이 검사는 tenant 권한을 대체하는 인증 주장이 아니라,
  기관 전환 후 이전 초안을 잘못 수정하지 않게 하는 자원 범위 통제다.
- Streamlit에서 기관을 바꾸면 이전 프로젝트 선택과 대기 선택을 지운다.
- 현재 기관의 어느 초안이든 미저장 입력이나 충돌이 있으면, 그 초안이 현재
  선택되어 있지 않아도 기관 전환을 즉시 실행하지 않고 경고·명시 확인을 요구한다.

### 오래된 화면의 덮어쓰기

- 프로젝트는 1부터 시작하는 단조 증가 개정 번호를 갖는다.
- 모든 변경과 상태 전이에는 `expected_revision`이 필요하다.
- 저장소의 현재 개정과 다르면 어떤 파일이나 이벤트도 쓰지 않고 충돌로
  처리한다.
- 로컬 편집기는 기본정보·조문·확인 목록별로 입력을 처음 불러온 기준 개정을
  고정한다. 미저장 입력이 있는 동안 서버 개정이 바뀌어도 기준을 자동으로 올리지
  않으며, 모든 저장·검사·상태 변경을 막고 명시적인 최신본 불러오기를 요구한다.
- Streamlit 위젯 수명과 별도의 세션 버퍼를 초안·입력 구역별로 유지한다. 다른
  초안을 선택하거나 한 구역을 먼저 저장해 위젯이 사라져도 나머지 미저장 값을
  복원하며, 같은 초안에서 한 구역 저장이 성공하면 다른 미저장 구역의 기준 개정만
  그 결과 개정으로 이동한다. 이 이동은 외부 변경에 대한 자동 재결합이 아니라,
  사용자가 방금 성공시킨 서로 겹치지 않는 로컬 구역 저장에만 적용한다.
- 위젯·버퍼·dirty·기준 개정·검사·내보내기 세션 키는 tenant·기관 프로필·프로젝트
  UUID를 모두 포함한다. 이전 버전의 범위 없는 브라우저 키는 새 프로젝트에
  재사용하지 않고 폐기해, 복원 등으로 서로 다른 tenant에 같은 UUID가 생겨도
  미저장 문장이나 파일이 섞이지 않게 한다.
- 수정 요청·자체 확인·작성 중단 사유도 action 구역의 세션 버퍼와 기관 전환
  경고에 포함한다. 확인 체크는 버퍼링하지 않아 프로젝트로 돌아온 사람이 다시
  명시해야 하며, 상태 전이 또는 중단 성공 뒤에는 해당 action 버퍼를 지운다.

### 자기 확인과 공식 승인 오인

- 보호 환경에서는 생성·수정·재개·확인요청 이벤트에 참여한 작성 행위자가 같은
  개정본을 동결할 수 없다.
- 로컬 연습 모드에서도 자기 동결은 기본 거절한다.
- 로컬 자기 동결은 요청자가 `allow_training_self_freeze=true`를 명시하고 사유를
  제공한 경우에만 허용한다.
- 이 예외를 사용한 프로젝트와 모든 후속 산출물에는 연습용 상태와 `공식 승인
  아님` 표시를 영구 보존한다. JSON은 `training_only=true`, Markdown은
  `연습용 표시: 예`를 사용한다.
- 작성 스키마는 기존 공식 흐름의 `approved`, `approval_id`,
  `approved_content_hash` 필드를 사용하지 않는다.

### 동결 후 바꿔치기

- 동결은 canonical semantic payload의 SHA-256과 개정 번호를 manifest에 기록한다.
- 저장소는 매 commit과 read에서 선언된 semantic SHA-256을 실제 canonical payload로
  다시 계산한다. 일치하지 않으면 manifest나 새 이벤트를 공개하지 않는다.
- 내보내기는 현재 프로젝트 본문이 아니라 tenant·기관 프로필 범위를 재확인해
  정확한 동결 개정의 불변 snapshot을 다시 읽고 렌더링한다.
- 스냅샷 또는 manifest의 해시가 다르면 내보내기를 거절한다.
- 새 세션에서 패키지를 다시 받을 때는 파일 SHA-256뿐 아니라 동결 snapshot에서
  다시 렌더링한 바이트와도 비교해 과거의 불일치 산출물을 거절한다.
- 브라우저의 다운로드 캐시도 tenant·기관·프로젝트·동결 개정·의미 내용 해시·파일
  해시와 현재 `exported` 상태가 모두 맞을 때만 표시한다. 재개하면 즉시 지우며,
  재동결 뒤 새 내보내기 전에는 과거 개정 파일을 현재 파일처럼 보여주지 않는다.
- 다시 편집하면 이전 스냅샷을 덮어쓰지 않고 새 개정으로 돌아간다.

### 불완전 저장과 감사 공백

- P0 조문 골격의 ID·유형·부모·순서·번호·제목·필수 여부·쉬운말 안내는 서버가
  소유한다. 클라이언트는 조문 본문과 근거 연결만 갱신할 수 있고, 조문 추가·삭제·
  재정렬 또는 구조 필드 변경은 저장 전에 거절한다.
- 작성자 확인 목록의 항목 ID·문구·순서는 서버가 소유하며, 사용자는 완료 여부와
  메모만 갱신할 수 있다. 목록 삭제·대체·이름 변경은 저장 전에 거절한다.
- 프로젝트 스냅샷은 같은 디렉터리의 임시 파일을 `fsync`한 뒤 원자 교체한다.
- 프로젝트 변경과 이벤트 추가는 하나의 논리 트랜잭션으로 취급한다.
- 새 snapshot과 event 불변 파일은 manifest가 가리키기 전에 바이트 일치와 event
  hash chain을 재검증한다. 이 사전 공개 검증이 실패하면 두 staged 파일을 지우고
  이전 manifest를 유지하므로 실패 응답 뒤 상태가 바뀌지 않는다.
- 최초 민감 snapshot을 쓰기 전에는 project·tenant·기관 프로필만 담고 본문은 없는
  staging intent를 원자적으로 기록한다. 최초 manifest가 공개되면 intent를 지우며,
  강제 종료로 intent나 manifest 없는 generation이 남으면 다음 저장소 시작 또는
  기관 삭제에서 같은 잠금 아래 복구·삭제한다.
- 이벤트에는 actor, tenant, revision, 이전·다음 상태와 내용 해시를 남긴다. 전이
  사유 자유문은 불변 이벤트에 저장하지 않고 `reason_supplied`와 SHA-256만 남긴다.
  수정 요청 문구는 권한이 확인된 tenant 프로젝트 snapshot에만 보관하며 초안
  본문과 함께 보호한다.
- schema v2 이벤트 metadata는 상태·건수·형식·해시 등 정해진 allowlist만
  허용한다. 상태는 상태 머신 enum, 해시는 소문자 SHA-256, 플래그는 JSON boolean,
  린트 건수는 0 이상의 정수, 내보내기 형식은 `json` 또는 `markdown`이어야 한다.
  서로 의미가 연결된 이전·다음 상태, 사유 제공 여부·해시, 내보내기 형식·파일
  해시는 짝으로만 저장하며 `to_status`는 실제 snapshot 상태와 같아야 한다. 임의의
  `message`, `feedback` 같은 별칭이나 허용 키에 초안 문자열을 넣는 요청도 저장 전에
  거절한다.
- 이전 schema v1 이벤트에 자유문 사유가 남아 있으면 저장된 hash chain을 먼저
  검증한 뒤 읽기 응답에서는 본문을 숨기고 `read_model_redacted=true`로 표시한다.
  과거에 허용됐지만 v2에서 알 수 없는 metadata도 값 자체를 반환하지 않고 원본
  metadata의 SHA-256과 `legacy_metadata_redacted=true`만 제공한다. 이때 event hash는
  변조하지 않은 저장 원본을 가리키므로 읽기용 투영과 원본 무결성 검증을 구분한다.
- API 감사 로그에는 프로젝트 UUID와 결과만 남기고 본문, 로컬 절대 경로,
  인증정보를 쓰지 않는다.
- 작성 API의 schema validation 422 응답은 오류 종류와 요청 영역만 공개하고
  입력값·임의 필드명은 반사하지 않는다. 본문 크기 413과 함께 내용 없는 거절
  감사 레코드를 남긴다. 대용량 파일 streaming 예외는 `POST /api/documents`의
  multipart 업로드에만 적용하며 `/api/authoring`은 위장한 multipart도 byte cap을
  우회할 수 없다.
- API와 로컬 화면에서 받은 검토·전이 사유에 절대 경로가 있으면 이벤트 저장 전에
  사유 전체를 고정 안내문으로 바꾼다. URL은 로컬 경로로 오인하지 않는다.

### 기관 삭제 뒤 남는 초안

- 기관 데이터 삭제 계획에 같은 tenant·기관 프로필의 작성 프로젝트 수도 포함한다.
- 활성 manifest를 먼저 제거하고 내용이 없는 purge tombstone을 남겨 부분 실패를
  다음 삭제 시도에서 발견하고 이어서 처리한다.
- export artifact 쓰기와 `EXPORTED` snapshot·event·manifest 공개는 기관 삭제와
  동일한 저장소 잠금 안에서 처리한다. 삭제가 먼저 끝나면 내보내기가 새 파일을
  만들 수 없고, 내보내기가 먼저 끝나면 삭제의 최종 sweep가 그 파일까지 지운다.
- snapshot, event, export 삭제가 모두 끝나기 전에는 기관 프로필 삭제를 완료로
  보고하지 않는다.
- 삭제 경로는 authoring 루트 안의 UUID 디렉터리로 제한하고 symlink를 거절하며,
  다른 기관 프로필과 tenant의 데이터는 보존한다.

### AI 제안의 무검토 반영

- P0은 외부 AI 호출을 제공하지 않는다.
- P1의 AI 출력은 suggestion과 provenance로만 저장하고 사람의 명시적 수락 전에는
  canonical 본문에 합치지 않는다.
- AI 실패는 수동 작성 경로를 차단하지 않는다.

### 공식 RAG/MCP 유입

- 작성 데이터는 기존 전처리와 벡터 색인 코드가 탐색하지 않는 별도 경로에 둔다.
- authoring API와 서비스는 공식 승인 또는 색인 함수를 호출하지 않는다.
- 회귀 테스트는 작성 전체 흐름 전후의 승인 저널·승인 벡터가 동일함을 확인한다.

## 상태 전이 보안 규칙

| 현재 상태 | 허용 다음 상태 | 추가 조건 |
|---|---|---|
| `planning` | `drafting`, `abandoned` | 필수 기본정보 저장 후 작성 시작 또는 사유를 남기고 빈 초안 중단 |
| `drafting` | `review_requested`, `abandoned` | 검토 요청 시 오류 등급 린트 0건 및 작성자 확인 목록 완료 |
| `changes_requested` | `drafting`, `abandoned` | 수정 시 새 개정 생성 |
| `review_requested` | `changes_requested`, `content_frozen` | 동결 시 개정 일치, 린트·체크리스트 통과, 4-eyes |
| `content_frozen` | `drafting`, `exported` | 내보내기 전 manifest 해시 재검증 |
| `exported` | `drafting` | 기존 동결·내보내기 보존 |

`abandoned`는 종단 상태다. 거절된 전이도 API 감사 로그에 남긴다.

## 배포 시 별도 검증 항목

애플리케이션 코드만으로 운영체제 파일 ACL, 백업 보존, 감사 로그의 외부 WORM
저장, 운영자 계정 분리까지 보장할 수 없다. 보호 배포 전에 다음을 별도로
확인한다.

- authoring 디렉터리의 계정별 최소 권한과 백업 암호화
- API token의 actor·tenant 바인딩과 작성자/확인자 계정 분리
- 감사 로그 중앙 전송 또는 변경 불가 보존
- 초안 보존 기간과 안전한 삭제 절차
- P1 import 전에 frozen manifest 서명 또는 동등한 무결성 통제
